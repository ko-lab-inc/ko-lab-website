**Résistance à l'usurpation d'IP — testée contre la PRODUCTION réelle
(`ko-lab-website.vercel.app`), pas en local :**

```
8 requêtes vers /api/contact, une adresse x-forwarded-for DIFFÉRENTE à chaque appel
→ refus (429) au 6ᵉ appel quand même, plafond identique à une IP unique
```

Résultat inattendu et positif : le commentaire de `adresseClient.ts` suppose
qu'sans Cloudflare en frontal, `x-forwarded-for` resterait falsifiable. Ce
n'est **pas** ce qui a été observé — Vercel semble réécrire cet en-tête avec
l'IP réellement connectée, indépendamment de ce que le client envoie. Le
compteur a tenu identiquement avec 8 adresses différentes. À documenter
dans le code (le commentaire actuel est plus pessimiste que la réalité
mesurée), sans pour autant s'y fier à 100 % — Vercel pourrait changer ce
comportement sans préavis, ce n'est pas une garantie contractuelle.

Panneau connu et déjà documenté dans le code, toujours vrai : le compteur vit
en mémoire de process (`Map`), donc par instance serverless — sur Vercel,
plusieurs instances chaudes partagent le même trafic sans partager leur
compteur. Le plancher réel est `N × plafond`, pas le plafond seul.

### Résultat de la requête 4 (Christian, 2 août)

`ajuster_stock_ligne_commande` (0023), `restaurer_stock_commande_annulee`
(0023/0025) et `interdire_auto_promotion` (0019) ont un `proacl` NULL — donc
EXECUTE accordé à PUBLIC par défaut, `anon` et `authenticated` compris. Les
trois sont `SECURITY DEFINER`.

**Sondé avant toute conclusion** (pas supposé) :

```
POST /rest/v1/rpc/ajuster_stock_ligne_commande      -> 404 PGRST202
POST /rest/v1/rpc/interdire_auto_promotion          -> 404 PGRST202
POST /rest/v1/rpc/restaurer_stock_commande_annulee  -> 404 PGRST202
```

Pas 401/403 — 404, « fonction introuvable ». PostgREST exclut de son
catalogue RPC toute fonction `RETURNS TRIGGER`, **indépendamment du GRANT** :
ce ne sont pas des fonctions appelables comme un `SELECT` normal (`NEW`/`OLD`/
`TG_OP` n'existent qu'en contexte de déclencheur réel). **Verdict : pas
exploitable aujourd'hui via `/rpc/`.** Le correctif (migration 0026, ci-dessous)
est de la défense en profondeur — retirer un privilège qui n'aurait jamais dû
être accordé, pas fermer une brèche active.

**Migration `0026_revoke_execute_fonctions_trigger.sql` écrite ET exécutée le
2 août.** `revoke execute ... from public, anon, authenticated` sur les trois
fonctions. Ne touche pas au fonctionnement des déclencheurs eux-mêmes — le
moteur de triggers de Postgres n'emprunte pas le chemin GRANT/EXECUTE.
**Resondé après exécution : même 404, code et message identiques** — aucun
changement de comportement, comme prévu.

### Résultat de la requête 2 — GRANT réels de `anon` (Christian, 2 août)

```
candidatures       INSERT, TRIGGER, REFERENCES, TRUNCATE
commandes          TRUNCATE, TRIGGER, REFERENCES
demandes_contact   INSERT, TRUNCATE, REFERENCES, TRIGGER
lignes_commande    TRIGGER, TRUNCATE, REFERENCES
postes_carrieres   REFERENCES, TRIGGER, SELECT, TRUNCATE
produits_boutique  REFERENCES, TRIGGER, SELECT, TRUNCATE
profils            TRUNCATE, TRIGGER, REFERENCES
realisations       REFERENCES, TRUNCATE, SELECT, TRIGGER
reglages           TRUNCATE, TRIGGER, SELECT, REFERENCES
videos             TRUNCATE, SELECT, TRIGGER, REFERENCES
```

**TRUNCATE, TRIGGER et REFERENCES sur les 10 tables sans exception** — y
compris `commandes`, `lignes_commande` et `profils`, qui n'ont par ailleurs
**aucun** GRANT CRUD pour `anon` (conforme à ce que prévoient 0004/0021 : la
ligne SELECT/INSERT/UPDATE/DELETE est absente pour ces trois-là, exactement
comme annoncé). Ce constat élimine l'hypothèse d'un oubli dans une migration
précise : les 26 migrations ont été relues, chaque `grant` à `anon`/`authenticated`
s'est toujours limité à SELECT/INSERT/UPDATE/DELETE/USAGE, jamais ces trois-là,
et aucun `grant ... to public` (le rôle) n'existe qui aurait pu se répercuter
sur `anon`. Présents uniformément sur toutes les tables sans qu'aucun `grant`
tracé ne les explique : un réglage par défaut posé au niveau du schéma, hors
de tout fichier de ce dépôt — jamais documenté, comme `rls_auto_enable` (0020).

**Pourquoi ça compte.** TRUNCATE vide une table entière d'un coup — RLS ne
s'applique pas à cette commande, seulement à SELECT/INSERT/UPDATE/DELETE. Un
`anon` qui l'aurait aurait pu vider `commandes` ou `demandes_contact`
intégralement, RLS actif ou non. TRIGGER permet de poser un déclencheur sur
la table ; REFERENCES, une contrainte de clé étrangère pointant vers elle —
aucun usage légitime pour `anon`/`authenticated` sur ce projet.

**Migration `0027_revoke_truncate_trigger_references.sql` écrite ET exécutée
le 2 août.** `revoke` large sur `all tables in schema public`, plus `alter
default privileges` pour qu'une future table n'hérite pas du même trou. Non-
régression revérifiée juste après (`node scripts/audit-supabase.mjs`) : même
résultat qu'avant le correctif sur tout ce qui est sondable via REST — SELECT/
INSERT/UPDATE/DELETE inchangés sur les 10 tables, storage inchangé, rôles
inchangés. La disparition effective de TRUNCATE/TRIGGER/REFERENCES elle-même
n'est vérifiable qu'en SQL direct (PostgREST n'expose aucune de ces trois
opérations via son API REST, donc aucune sonde HTTP possible côté client) —
requête de vérification dans le fichier de migration, résultat à confirmer
par Christian.

Les 2 dernières requêtes (policies réelles, tables sans RLS) : résultat
toujours en attente.
